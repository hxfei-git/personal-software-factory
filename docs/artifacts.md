# Artifact Strategy

Artifacts preserve the evidence and files produced by planning, workers, QA, bugs, and release preparation. They must be addressable from the API/Hub without forcing large files into the database.

## Storage Policy

Small text artifacts may be stored inline in `Artifact.content` when doing so improves inspection and tests. Current examples include:

- `mission.md`
- `acceptance.md`
- `technical-notes.md`
- `risk-notes.md`
- `codex-prompt.md`
- `codex-command.sh` review artifact
- `dev-summary.md`

Large or binary artifacts must be stored path-only with metadata, not inline content. Examples:

- screenshots;
- Playwright traces;
- HTML reports;
- long logs;
- archives;
- generated videos;
- large JSON reports.

For path-only artifacts, keep these fields accurate:

- `path`
- `type`
- `size`
- `mime_type`
- `metadata`
- optional `worker_run_id`

## Path Boundaries

Local generated artifacts for real-mode workers use the canonical worker-run scoped path:

```text
artifacts/missions/<mission-id>/<worker-run-id>/<category>/<filename>
```

Supported categories are `mission`, `codex`, `qa`, `fix`, `deploy`, `monitor`, `integration`, and `logs`. New real-mode writes must use this canonical path through `@psf/artifact-store`; the older demo path remains legacy-readable only:

```text
missions/<mission-id>/<filename>
```

Worker project clones belong under:

```text
workspaces/<project-id>/
```

Do not store artifacts outside the repository-managed roots unless a later object-storage policy explicitly documents the location and access controls.

Artifact paths should be stable, relative, and free of secrets. Avoid spaces in generated paths. The artifact store returns database-facing paths relative to the repository root, while filesystem writes are resolved under the absolute `artifacts/` root.

## Content Boundaries

Artifact content must not include:

- API tokens;
- provider keys;
- cookies;
- database passwords;
- private deployment credentials;
- raw `.env` content;
- unredacted logs containing sensitive values.

Prompts, logs, PR bodies, QA reports, and comments must use redacted values when environment or credential-like strings are relevant.

## Database Boundary

The database may store inline content for small markdown/text review artifacts. It should not be used as a blob store. When a file is large, frequently rewritten, binary, or generated by QA tooling, store the path and metadata in the database and keep the file in the artifact root.

Current API behavior accepts `content` for `POST /missions/:missionId/artifacts`, but callers are responsible for applying this size and sensitivity policy. Real-mode workers should prefer `saveTextArtifact` for small text artifacts and `savePathArtifact` for binary, large, or externally generated evidence. `saveTextArtifact` redacts content before writing and before returning `Artifact.content`; `savePathArtifact` returns path-only metadata and does not read large source content.

## Current Batch

The current dry-run batch stores planner and Codex review artifacts as small text records and local mission files. QA screenshots, traces, Playwright reports, and large logs are not implemented yet and should be path-only when added.

## QA Artifacts

QA Worker dry-run writes small text artifacts inline where useful: `qa-report.md`, `bugs.json`, `qa-summary.json`, and `generated-regression.spec.ts`. Screenshot, trace, and log directories are path-only artifacts and currently contain placeholder `.gitkeep` files.

Auto Fix Loop dry-run writes `fix-mission.md`, `fix-acceptance.md`, `fix-codex-prompt.md`, and `fix-codex-command.sh`. The command file is review-only and must not be executable.

## Hub And Integration Artifacts

Hub Web reads existing Mission, QA, BugReport, WorkerRun, and Artifact records through `GET /dashboard` and `GET /missions/:id/summary`. It should render artifact metadata and inline text safely, but it must not create a second storage location or copy secrets into browser state.

Integration dry-runs currently return simulated payloads directly from the API/CLI. They do not create durable Artifact records by themselves. If a later phase stores integration preview payloads as artifacts, keep them small, text-based, and redacted:

- GitHub PR and Issue preview bodies may be inline markdown only after token and password redaction.
- Coolify deploy previews should store request summaries, not provider credentials.
- Uptime Kuma monitor previews should store target URLs and monitor settings, not usernames or passwords.
- Plane issue previews should store Mission/Bug summaries and links, not API tokens.

Large provider responses, webhook payloads, or binary evidence should remain path-only under `artifacts/missions/<mission-id>/<worker-run-id>/integration/` with redacted metadata.

## Real-Mode Artifact Store

`@psf/artifact-store` centralizes real-mode artifact paths and retention metadata. It builds canonical paths under `artifacts/missions/<mission-id>/<worker-run-id>/<category>/<filename>` and uses `@psf/security` path guards and redaction helpers instead of duplicating safety logic.

Retention classes are:

- `short`: temporary logs, screenshots, traces, and short-lived binary evidence.
- `mission`: mission-scoped text artifacts that should remain available while the Mission is useful for audit and review.
- `release`: release or deployment evidence retained longer than a Mission-local artifact.
- `audit`: audit evidence with no automatic expiry.

Retention cleanup must run as a dry-run preview first. Deletion is allowed only when explicitly requested with non-dry-run options, and cleanup refuses any candidate path outside the configured artifacts root.
